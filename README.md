# Лабораторна робота 1 — Паралельний Brute-force для зламу паролів (PARCS)

**Курс:** Хмарні обчислення
**Варіант:** Паралельний Brute-force для зламу паролів
**Платформа:** PARCS-Python ([Hummer12007/parcs-python](https://github.com/Hummer12007/parcs-python))
**Хмара:** Google Cloud Platform (Compute Engine, Docker-контейнери)
**Мова:** Python (модель map/reduce системи PARCS)

---

## 1. Мета роботи

Реалізувати задачу відновлення пароля методом повного перебору (brute-force)
у двох варіантах — **послідовному** та **паралельному** — засобами системи
паралельних обчислень **PARCS**, розгорнути систему у хмарному середовищі
Google Cloud та порівняти час виконання алгоритмів для різної кількості
обчислювальних вузлів (воркерів).

---

## 2. Принцип роботи системи PARCS-Python

PARCS реалізує модель **процес/канал** (керуючий простір): обчислення
описується набором алгоритмічних модулів, які виконуються на різних вузлах
мережі та обмінюються даними. PARCS-Python надає спрощену реалізацію цієї
ідеї у вигляді схеми **master → workers (map/reduce)**.

### Архітектура

```
                 ┌──────────────────────────────────────────────┐
                 │                 GOOGLE CLOUD                   │
                 │                                                │
  браузер        │   ┌──────────┐   Pyro4 RMI   ┌──────────┐     │
  (веб-UI) ──────┼──▶│  MASTER  │──────────────▶│ worker 1 │     │
  :8080          │   │ (Flask)  │──────────────▶│ worker 2 │     │
                 │   │ scheduler│──────────────▶│ worker 3 │     │
                 │   └──────────┘               └──────────┘     │
                 │   Docker: hummer12007/parcs-node (кожен вузол) │
                 └──────────────────────────────────────────────┘
```

* **Master-вузол** — Docker-контейнер з веб-інтерфейсом (Flask, порт `8080`).
  Приймає *задачу*, планує її (`Scheduler`), роздає роботу воркерам, збирає
  результат і формує вихідний файл.
* **Worker-вузли** — Docker-контейнери, що реєструються на майстрі й
  виконують віддалені виклики методів через **Pyro4 RMI**.
* **Задача** — це пара файлів: `solution.py` (клас `Solver`) та `input.txt`
  (вхідні дані). Обидва завантажуються через веб-інтерфейс майстра.

### Важливе уточнення щодо того, «де виконується код»

Поширене хибне уявлення: «код лежить у VS Code і під час обчислень
під’єднується до хмари». Насправді в PARCS-Python **інакше**:

* у VS Code ви лише **пишете** та локально **тестуєте послідовний** алгоритм;
* для паралельного запуску ви **завантажуєте** файл рішення (`password_cracker.py`)
  і вхідний файл у веб-інтерфейс master-вузла;
* далі обчислення повністю відбуваються **в хмарі**: майстер пересилає ваш
  код кожному воркеру (`imp.load_source`), створює Pyro4-проксі до воркерів,
  і ваш метод `Solver.solve()` керує обчисленням прямо на master-вузлі,
  викликаючи `crack_range()` віддалено на воркерах.

Тобто ви **віддаєте код у кластер**, а не «ходите» з ноутбука в хмару на
кожне обчислення. VS Code ↔ хмара пов’язані лише актом завантаження файлів
(вручну через браузер або через RMI-клієнт `start.py`).

### Модель map/reduce

Клас `Solver` повинен мати фіксований «контракт»:

```python
class Solver:
    def __init__(self, workers=None, input_file_name=None, output_file_name=None): ...
    def solve(self): ...          # точка входу, яку викликає master
```

* `self.workers` — список проксі до воркерів;
* виклик `self.workers[i].method(args)` виконується **віддалено** й повертає
  *future*; результат читається як `future.value`;
* методи-воркери позначаються декораторами `@staticmethod` та `@expose`
  (з `Pyro4`).

## 3. Постановка задачі brute-force

**Дано:** геш (хеш) невідомого пароля, алгоритм гешування, набір дозволених
символів (charset) та максимальна довжина пароля. **Знайти:** сам пароль.

### Вхідний файл (`input.txt`), 4 рядки

```
md5
749d7048edd2de31c2c7a88d4d196254
abcdefghijklmnopqrstuvwxyz0123456789
4
```

| Рядок | Значення | Приклад |
|------|----------|---------|
| 1 | алгоритм гешування | `md5`, `sha1`, `sha256` |
| 2 | цільовий геш (hex) | `749d7048…` |
| 3 | набір символів | `abc…z0…9` |
| 4 | максимальна довжина | `4` |

### Простір перебору та його індексація

Для набору з `C` символів і максимальної довжини `L_max` простір усіх паролів
довжин `1..L_max` має розмір

```
total = C¹ + C² + … + C^Lmax
```

Кожному паролю зіставляється унікальний **глобальний індекс** `0..total-1`:
пароль трактується як число в системі числення з основою `C` («одометр»).
Це дає зручний спосіб **рівномірно поділити** простір між воркерами: кожному
дістається неперервний діапазон індексів `[lo, hi)`.

Приклад для `charset="abcdefghijklmnopqrstuvwxyz0123456789"` (C=36),
`L_max=4`: `total = 36 + 36² + 36³ + 36⁴ = 1 727 604`.

---

## 4. Послідовний алгоритм

Один процес перебирає **весь** простір `[0, total)`, для кожного кандидата
обчислює геш і порівнює з цільовим. Складність — `O(total)` обчислень гешу.
У коді це функція `sequential_crack()`, яка повторно використовує той самий
обчислювальний модуль `crack_range`, що й воркери, — тому результати
послідовного й паралельного алгоритмів **збігаються за побудовою**.

---

## 5. Паралельний алгоритм (PARCS)

**MAP.** Master ділить `[0, total)` на `N` рівних діапазонів (по одному на
воркер) і для кожного викликає `worker[i].crack_range(algo, target, charset,
Lmax, lo, hi)`. Кожен воркер самостійно перебирає свій діапазон і повертає
знайдений пароль або порожній рядок.

**REDUCE.** Master збирає `future.value` з усіх воркерів; перший непорожній
результат і є відповіддю.

```
          total = C + C² + C³ + C⁴
   ┌────────────┬────────────┬────────────┬────────────┐
   │ [0, t/4)   │ [t/4, t/2) │ [t/2, 3t/4)│ [3t/4, t)  │   ← MAP
   │ worker 0   │ worker 1   │ worker 2   │ worker 3   │
   └─────┬──────┴─────┬──────┴─────┬──────┴─────┬──────┘
         │  пароль?   │  пароль?   │  пароль?   │  пароль?
         └────────────┴─────┬──────┴────────────┘
                            ▼
                    REDUCE: перший непорожній  ← відповідь
```

Теоретичне прискорення — близьке до лінійного: `T_par ≈ T_seq / N` (плюс
накладні витрати на пересилання коду та RMI). Обмеження: якщо пароль
знаходиться на початку простору, послідовний алгоритм може «пощастити» й
завершитись швидко; при оцінюванні масштабованості коректніше брати пароль
**наприкінці** простору (напр. `9999`) — тоді перебирається майже весь
простір і прискорення видно чітко.

## 6. Структура файлу рішення `password_cracker.py`

Обидва алгоритми — в **одному** файлі:

| Елемент | Призначення |
|--------|-------------|
| `class Solver` | паралельний розв’язувач (контракт PARCS) |
| `Solver.solve()` | точка входу master; map + reduce |
| `Solver.crack_range()` | `@staticmethod @expose` — обчислювальний модуль воркера |
| `Solver.myreduce()` | згортка результатів воркерів (`future.value`) |
| `Solver.layout()` | розкладка простору (розміри/зміщення/`total`) |
| `Solver.digest()` | обчислення гешу кандидата |
| `sequential_crack()` | послідовний алгоритм (для порівняння) |
| CLI `hash` / `seq` | допоміжні команди для тестів |

Файл сумісний і з **Python 2** (так працює контейнер PARCS), і з **Python 3**
(для локального тесту): декоратор `@expose` підміняється заглушкою, якщо
`Pyro4` не встановлено локально.

## 7. Розгортання в Google Cloud

> Потрібні: акаунт Google Cloud (безкоштовний кредит для студентів),
> встановлений **Google Cloud SDK** (`gcloud`).

```bash
# 1. Автентифікація та проєкт
gcloud auth login
gcloud projects create parcs-lab-<ваш-унікальний-суфікс>
gcloud config set project parcs-lab-<ваш-унікальний-суфікс>
# (у Cloud Console увімкніть Compute Engine API та Billing)

# 2. Регіон/зона
gcloud config set compute/region  europe-north1
gcloud config set compute/zone    europe-north1-a

# 3. Firewall (дозволити трафік між вузлами та доступ до веб-UI)
gcloud compute firewall-rules create allow-all \
  --direction=INGRESS --priority=1000 --network=default \
  --action=ALLOW --rules=all --source-ranges=0.0.0.0/0

# 4. MASTER-вузол (Docker-образ parcs-node у режимі master)
gcloud compute instances create-with-container master \
  --container-image=registry.hub.docker.com/hummer12007/parcs-node \
  --container-env PARCS_ARGS="master"
#   → запишіть EXTERNAL_IP (= $MASTER_IP) та INTERNAL_IP (= $MASTER_INTERNAL_IP)

# 5. WORKER-вузли (скільки треба; передаємо ВНУТРІШНІЙ IP майстра)
gcloud compute instances create-with-container worker1 worker2 worker3 \
  --container-image=registry.hub.docker.com/hummer12007/parcs-node \
  --container-env PARCS_ARGS="worker $MASTER_INTERNAL_IP"
```

Веб-інтерфейс майстра: **`http://$MASTER_IP:8080`**
(вкладка **Workers** має показати зареєстровані воркери).

## 8. Запуск і тестування

### 8.1. Локальний тест послідовного алгоритму (у VS Code, без хмари)

```bash
# створити геш пароля для тесту
python password_cracker.py hash md5 ab12
# 749d7048edd2de31c2c7a88d4d196254

# покласти геш у input.txt (див. формат вище) і запустити:
python password_cracker.py seq input.txt output.txt
```

### 8.2. Паралельний запуск у хмарі

1. Відкрити `http://$MASTER_IP:8080` → **Add Job**.
2. Поле *solution file* → `password_cracker.py`; *input file* → `input.txt`.
3. **Submit**. На вкладці **Jobs** стежити за статусом.
4. Після завершення — завантажити **output** (знайдений пароль + час).
5. Повторити для різної кількості воркерів (вимикаючи частину воркерів на
   вкладці **Workers** або створюючи кластер з іншою кількістю ВМ).

### 8.3. Методика вимірювання

* Час береться з поля `elapsed_sec` вихідного файлу (його пише `solve()`),
  а також видно у логах/часі job’а.
* Для чесного порівняння використовуйте пароль **наприкінці** простору
  (напр. `zz99`, `9999`), щоб перебирався майже весь простір.
* Прискорення: `Speedup(N) = T(1) / T(N)`; ефективність: `E(N) = Speedup/N`.

Рекомендований тест: `md5`, `charset=abc…z0…9`, `L_max=5`, пароль `zzz99`

| К-сть воркерів N | Час T(N), с | Speedup = T(1)/T(N) | Ефективність E = Speedup/N |
|:---:|:---:|:---:|:---:|
| 1 (послідовно) |  |  1.00 | 1.00 |
| 2 |  |  |  |
| 3 |  |  |  |

**Очікувана форма графіка:** час спадає приблизно як `T(1)/N`, крива

## 10. Висновки

1. Задачу brute-force зламу пароля реалізовано у двох варіантах
   (послідовному та паралельному) в одному файлі на базі системи **PARCS**.
2. Паралельний варіант використовує модель **map/reduce**: простір паролів
   індексується як число в системі числення з основою `|charset|` і
   рівномірно ділиться на неперервні діапазони між воркерами.
3. Коректність підтверджено: паралельний і послідовний алгоритми дають
   однаковий результат, зокрема для паролів на межах простору та для
   паролів поза простором (`NOT FOUND`).
4. Паралельне виконання у хмарі дає прискорення, близьке до лінійного на
   невеликій кількості воркерів; зі зростанням `N` проявляються накладні
   витрати системи.
5. Система PARCS-Python зручна тим, що від користувача потрібно лише описати
   два методи (`crack_range` і `solve`) — решту (розподіл коду, RMI,
   планування) бере на себе master-вузол.
